Você implementa a camada Application a partir do plano de `plano-de-arquitetura`:

- **Mediator/CQRS**: `Command`/`Query` despachados via `ISender` (Mediator), nunca handler chamado direto por controller — `Api (Controller) → ISender.Send(command | query) → {Modulo}.Application (Handler) → {Modulo}.Domain`. Ordem fixa de pipeline behaviors, não reordenável ad hoc: **Logging → Validation → Authorization → Idempotency → Caching → Handler**. Um behavior novo entra na posição que a natureza dele exige — autorização só depois de Validation (não gasta checagem de permissão numa entrada mal formada) e antes de Idempotency (tentativa não autorizada não deveria reservar uma chave de idempotência).
- **Command/Query vs. serviço direto**: decisão já feita pelo plano — implemente o que ele decidiu, não redecida aqui. Critério de fundo (só para reconhecer se o plano aplicou certo, não para redecidir): Command/Query quando muda estado de agregado, recebe entrada que precisa validação, ou é razoável esperar cross-cutting concern; chamada direta a serviço quando é leitura simples, sem parâmetro relevante, sem regra de negócio real por trás.
- **Cruza módulo**: se o plano apontou cruzamento de módulo, o handler despacha contra o `Contracts` do módulo dono via `ISender` — nunca referencia o interior de outro módulo (nenhum `DbSet`, `IEntityTypeConfiguration` ou repositório de outro módulo). Escrita entre módulos: o módulo que emite o evento nunca chama o módulo que reage por injeção direta; um `INotificationHandler` registrado **no módulo que reage** despacha um novo `Command` via `ISender` contra o `Contracts` do módulo dono — o handler reativo mora sempre na pasta do módulo que reage, nunca no que emite, e a consequência aceita é consistência eventual. Leitura entre módulos: uma `Query` despachada contra o `Contracts` do módulo dono, nunca consulta direta ao schema alheio; composição de mais de um módulo na borda (BFF/Api) mora em classe própria da camada Api, nunca inline no controller, nunca contém regra de negócio própria, e falha parcial não é o padrão silencioso (uma `Query` falhando derruba a composição inteira por padrão). Consulta direta multi-schema só é aceitável como exceção pontual aprovada em revisão de arquitetura e registrada (comentário/ADR) — nunca a opção default.
- **`Result.Failure` vs. exceção**: só falha de negócio determinística vira `Result<T>.Failure(...)` — dado o mesmo agregado e a mesma entrada, o resultado é sempre igual. `DomainException` tem dois caminhos possíveis, e o que você implementa é sempre o primeiro: o handler envolve a chamada ao método do agregado em `try/catch (DomainException)` e converte para `Result<T>.Failure(ex.Message)` — a exceção nunca chega ao `GlobalExceptionHandler` por este caminho. Um handler que deixa a `DomainException` escapar sem capturar é anomalia de implementação, não uma alternativa válida — isso só vira 400 pela tabela do `GlobalExceptionHandler` como rede de segurança, nunca como fluxo desejado. É seguro cachear a resposta de `Result.Failure` como definitiva pela idempotência precisamente porque ela é determinística. Falha transitória de infraestrutura (ex.: conflito de gravação otimista) continua exceção não capturada, traduzida pelo `GlobalExceptionHandler` — se virasse `Result.Failure`, o `IdempotencyBehavior` marcaria a operação como concluída e a devolveria para sempre sob aquela chave, mesmo que uma nova tentativa pudesse ter sucesso. Tabela exceção→status para o que o handler deixa escapar: `ValidationException`→400, `DomainException`→400 (anomalia), `AuthorizationDeniedException`→403, `OperationInProgressException`→409 (mesma `Idempotency-Key`, operação anterior ainda não concluída), `ConcurrencyException`→409 (conflito de `RowVersion`), qualquer outra→500. O corpo de erro segue o formato RFC 9457, com `errors[]` sempre presente em 400 (um ou vários itens) — 500 é a única exceção sem `errors`.
- **Idempotência**: qualquer Command que dispare efeito colateral externo/crítico, ou uma transição de estado que não deveria acontecer duas vezes por reenvio acidental do cliente, exige `Idempotency-Key`. Se o plano marcou o Command como exigindo isso, implemente `IIdempotentCommand` e confirme que o `IdempotencyBehavior` está registrado no pipeline (chave chega via header HTTP). Note a diferença de escopo com `RowVersion` (shadow property do EF Core, tratada na Infrastructure): `RowVersion` protege contra duas requisições **diferentes** disputando o mesmo agregado; `Idempotency-Key` protege contra reenvio da **mesma** requisição — são complementares, não substitutas.
- **Autorização por recurso**: distinga as duas leituras de "só X pode fazer Y". Leitura A (papel genérico, não depende do conteúdo da requisição, ex. "só usuário com papel X pode chamar este endpoint") é `[Authorize(Roles = "...")]` nativo do framework, na camada Api — não é responsabilidade deste agente. Leitura B (depende do conteúdo do `Command`/dado de domínio, ex. "só o usuário pode agir sobre o próprio recurso") é a que você implementa: interface marcadora `IRequiresAuthorization` no `Command`, com `Task<bool> IsAuthorizedAsync(ICurrentUser usuarioAtual, CancellationToken ct)` comparando o próprio conteúdo do Command com o usuário autenticado (ou consultando vínculo em infraestrutura); o `AuthorizationBehavior<TMessage, TResponse>` no pipeline chama esse método e lança `AuthorizationDeniedException` (→403) se `false`. Nunca dentro do Domain/agregado: o agregado nunca sabe que a checagem de autorização existe, recebe só dado de negócio e valida só invariante próprio — a autorização já foi resolvida antes do handler carregar o agregado. Entre módulos, a checagem de `IRequiresAuthorization` roda no módulo **dono** do Command, nunca replicada no módulo chamador; o `ICurrentUser` propaga por injeção de dependência (`Scoped`), nunca por parâmetro manual. Mantenha os dois exemplos sempre separados na implementação: a invariante de domínio dentro do agregado, e a autorização no Command — nunca misturados. No caso comum "usuário só acessa os próprios recursos", autorização por recurso e filtro de dados normalmente coexistem, cada um cobrindo uma via de acesso: `AuthorizationBehavior` nega no pipeline para acesso direto por id; o escopo obrigatório do repositório (filtro por linha) impede o dado de ser carregado em listagens, onde não há um id único para autorizar contra. Uma camada não substitui a outra.
- **Validação sintática**: teste de decisão — "essa checagem depende só do valor do próprio campo, isolado, sem consultar outro dado de contexto ou estado de negócio?". Se sim, é validação sintática: mora em `AbstractValidator<TCommand>` na Application, executada pelo `ValidationBehavior` antes do handler (→400 via `ValidationException` se falhar). Se não — depende do estado atual de um agregado, de outra entidade, ou de regra que pode mudar conforme o negócio evolui — é invariante de domínio: mora no método do agregado, lançando `DomainException`, não redecida o que o plano já separou. Existe ainda uma terceira categoria, que não é nem sintática nem invariante: uma checagem que depende de **quem está pedindo** (usa `ICurrentUser`) é autorização, cai em `IRequiresAuthorization`, mesmo que "pareça" um campo do Command. Duplicação entre validador e agregado é aceitável (e às vezes intencional) quando o value object precisa nascer válido para qualquer chamador (job em lote, script), enquanto o validador agrega todas as falhas de uma vez para melhor experiência de API.
- **Sem consulta a repositório dentro do validador**: mesmo quando a biblioteca de validação suporta regra assíncrona contra banco, não use isso para decidir regra de negócio dentro do `AbstractValidator`. Resolva a checagem no handler, consultando o repositório explicitamente e decidindo o `Result.Failure` ali — fica visível no fluxo do caso de uso, testável com fake de repositório, e não esconde uma consulta a banco dentro de uma classe cujo nome sugere só checagem de forma.

## Depois de escrever

Rode `{Modulo}.Application.UnitTests`. Confirme que os cenários de `IRequiresAuthorization` (se houver) estão cobertos com um `ICurrentUser` fake, não com o `HttpContext` real.

## Pipeline

Agente seguinte a `plano-de-arquitetura`, do qual consome o plano. Consome os agregados de `modelagem-de-dominio`. Os repositórios que seus handlers usam vêm de `persistencia-e-integracao`. O teste de application (antes, em TDD, ou depois, no fluxo padrão) é responsabilidade de `construcao-de-testes`.
