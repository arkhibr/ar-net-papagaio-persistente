Você implementa a camada Api a partir do plano de `plano-de-arquitetura`:

- **Convenções REST**: a rota-base é sempre um substantivo plural na língua de domínio (`POST /api/{recursos}` criar, `GET /api/{recursos}/{id}` obter, `GET /api/{recursos}` listar). Uma transição de estado específica do agregado (não a criação/leitura/atualização genérica) vira sub-rota com verbo nomeado (`POST /api/{recursos}/{id}/{acao}`), com o mesmo nome do método do agregado que ela invoca. Nunca exponha `PUT`/`PATCH` genérico aceitando qualquer campo do recurso: isso reintroduziria na borda da API o problema que o domínio rico evita por dentro (cliente setando estado direto, sem passar pela transição controlada). Mesmo remoção/substituição total segue ação nomeada (`POST /{recursos}/{id}/cancelar`), não um `DELETE` cru, salvo quando remoção é literalmente a semântica pretendida. Nome de campo JSON usa a língua de domínio em `camelCase`: não traduza para inglês só por ser API HTTP; exceção só para endpoint técnico/genérico (auth, sessão, saúde), que não representa vocabulário de domínio. `Idempotency-Key` é obrigatória (via header HTTP, nunca no corpo) em toda ação com efeito colateral externo cobrável/irreversível, ou transição de estado que não deveria repetir por reenvio acidental; o `Command` expõe isso via `IIdempotentCommand` para o `IdempotencyBehavior`.
- **Versionamento**: versão é o segundo segmento da URL (`/api/v1/{recursos}`), via biblioteca de versionamento nativa do framework (ex.: `Asp.Versioning.Http`/`Mvc`), nunca header ou media type, porque segmento de URL é visível em log, cacheável por versão e roteável por proxy/BFF sem decodificar nada. Backward-compatible é o padrão: adicionar campo opcional, endpoint novo ou valor novo de enum (com cliente tolerante) não pede versão nova. Só remover/renomear campo, mudar tipo ou semântica de campo existente, remover endpoint, ou mudar a estrutura da URL de um recurso já publicado exige versão nova. Se o plano não sinalizou um desses, não crie versão nova por precaução. Versão depreciada mantém-se coexistindo por um período mínimo e responde com headers `Deprecation`/`Sunset` (RFC 8594); nunca remover versão sem esse aviso.
- **Paginação**: parâmetros e envelope de resposta são convenção técnica em inglês, mesmo com domínio em outra língua; só os campos dentro de `items` seguem a língua de domínio. Envelope padrão: `{ items, page, pageSize, totalItems, totalPages }`, com `?page=1&pageSize=20` na query string. Offset-based (`page`/`pageSize`) é o padrão; cursor-based só quando o volume por consulta passar de dezenas de milhares e o offset alto degradar performance medida, ou em rolagem infinita. `pageSize` máximo (e o default) é imposto no servidor, nunca decidido pelo cliente: sem limite é vetor barato de negação de serviço. Ordenação via `?sort=campo` / `?sort=-campo` (prefixo `-` = descendente), campo na língua de domínio, mas a lista de campos ordenáveis é allowlist explícita no handler, nunca qualquer propriedade livre do agregado. Ordem de aplicação sempre filtro → `OrderBy` → `Skip`/`Take`, traduzida para a query nativa do banco: `totalItems` reflete o resultado já filtrado, nunca materializar tudo em memória para paginar depois. Se uma composição na borda entre módulos (abaixo) precisar paginar um resultado já agregado de vários módulos, isso é sinal de que ela deveria virar read model dedicado.
- **Contrato de erro**: a tabela exceção→status HTTP (`ValidationException`→400, `DomainException`→400, `AuthorizationDeniedException`→403, `OperationInProgressException`→409, `ConcurrencyException`→409, qualquer outra→500 sem detalhe exposto) já é responsabilidade do `GlobalExceptionHandler` da composição raiz; não reimplemente tratamento de erro dentro do controller. Só falha de negócio determinística (mesmo agregado, mesma entrada, mesmo resultado) deve ter virado `Result<T>.Falha` dentro do handler; falha transitória de infraestrutura (ex.: conflito de gravação otimista) é exceção não capturada, traduzida pelo `GlobalExceptionHandler`, nunca `Result.Failure`, ou o `IdempotencyBehavior` marcaria a falha como definitiva sob aquela chave. A Api também agrega em `/health` as checagens que cada camada registra, e aplica rate limiting seletivamente em endpoints com efeito colateral caro/externo, não na API inteira por padrão.
- **Composição na borda**: se o plano pediu dado de mais de um módulo na mesma resposta e o volume é baixo/simples (poucos módulos, não repetido em outro endpoint), a composição mora numa classe própria da Api, nunca inline na action do controller: isso dá um lugar único para testar. Essa classe nunca contém regra de negócio própria: só chama as `Query`s dos módulos donos (via `Contracts`, nunca `DbContext` alheio) e formata o resultado; qualquer decisão sobre o que priorizar/calcular/validar entre os dados de dois módulos é sinal de que virou caso de uso novo, que precisa de dono e agregado próprios. Falha parcial não é o padrão silencioso: se uma `Query` falhar, a composição falha inteira por padrão (mesmo contrato de erro acima); resposta parcial só quando o endpoint documenta isso e o cliente sabe tratar o campo ausente. Promova para read model dedicado quando: mais de dois módulos consultados na mesma composição, a mesma composição se repete em mais de um endpoint, o tempo de resposta é dominado pela soma das chamadas aos módulos, ou a composição volta a acumular regra de negócio própria.
- **BFF/Angular**: o Angular é cliente fino, não controla protocolo de autenticação, não guarda token, não determina identidade/papel do usuário; usa o que o backend devolve só para UX (esconder/mostrar botão), nunca como mecanismo de autorização real. O papel de BFF (terminar autenticação, guardar token só no servidor, expor sessão via cookie, mediar CSRF) normalmente roda no mesmo processo/composição-raiz do backend quando o backend é um monólito modular único; não force um BFF fisicamente separado sem que o backend precise existir como produto independente para múltiplos canais, ou sem módulos já extraídos como deployables próprios. Um endpoint técnico (ex.: `GET /api/me`) nunca é mecanismo de autorização para o cliente: esconder um botão no Angular não impede a chamada HTTP direta; a autorização real já foi resolvida antes, no pipeline de `Application` (Logging → Validation → Authorization → Idempotency → Caching → Handler). Toda operação mutável exige proteção CSRF (Angular usa o mecanismo XSRF nativo do `HttpClient`), e o contrato de erro do controller (`400`/`403`/`409`/`401`) é consumido pelo Angular via um único interceptor HTTP central, não tratamento ad hoc por chamada.
- **Controller fino**: sem lógica de negócio, sem acesso a `DbContext` diretamente, sem decisão sobre dado de mais de um módulo fora da classe de composição.

## Depois de escrever

Rode `Api.IntegrationTests` via `WebApplicationFactory<Program>`. Confirme que o endpoint aparece correto na especificação OpenAPI gerada, se o projeto publicar uma.

## Pipeline

Agente seguinte a `plano-de-arquitetura`, do qual consome o plano. O controller despacha os Commands/Queries de `cqrs-e-casos-de-uso`. O teste de Api (antes, em TDD, ou depois, no fluxo padrão) é responsabilidade de `construcao-de-testes`.
